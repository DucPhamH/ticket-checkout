# Database

[Tiếng Việt](vi/07-database.md)

PostgreSQL 16 through Prisma 7 (`apps/api/prisma/schema.prisma`, `pg` driver adapter).
One migration so far: `prisma/migrations/*_init`. Its first half is generated by Prisma; the
second half is hand-written SQL for rules Prisma's schema language cannot express.

## Tables

```
users ─┬─< listings >── events
       │      │
       │      └─< orders ──1:1── payments ──< payment_notifications
       │            │                 │
       │            └──1:1── refunds ─┘
       │
       └─< accounts ──< ledger_entries >── ledger_transactions
                                             (optionally linked to an order, event or refund)
```

| Table                                               | Purpose                                                                                                                     |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `users`                                             | Demo users; `role` is `USER` or `ADMIN`.                                                                                    |
| `events`                                            | `ACTIVE` → `COMPLETED` or `CANCELLED`, each with its timestamp.                                                             |
| `listings`                                          | A seller's tickets for an event. `quantity_available` is decremented on reservation.                                        |
| `orders`                                            | One purchase. Prices and fees are copied in at checkout and never recomputed.                                               |
| `payments`                                          | Gateway side of an order: our `txn_ref`, the provider's transaction number and pay date (needed for `querydr` and refunds). |
| `payment_notifications`                             | Every IPN, return redirect and status query, stored raw before it is acted on.                                              |
| `refunds`                                           | At most one (full) refund per order; retried until it succeeds.                                                             |
| `accounts`, `ledger_transactions`, `ledger_entries` | The double-entry ledger, see [Ledger](06-ledger.md).                                                                        |
| `account_balances` (view)                           | Balance per account, in its natural sign.                                                                                   |

`orders` and `payments` are separate on purpose: an order is our business object, a payment is
one provider's view of it. Adding a second gateway would not touch `orders`.

## Conventions

- snake_case in SQL, camelCase in TypeScript (`@map`/`@@map`).
- Money is `BIGINT` in whole VND. Prisma returns it as `bigint`; it is converted to `number` only
  when building API responses (safe up to 9e15 VND).
- Timestamps are `timestamptz(3)`.
- Integer identity keys. Foreign keys are `ON DELETE RESTRICT`: nothing that money depends on can
  be deleted from under it.
- Every foreign key has an index (Postgres does not create them automatically).

## Rules enforced by the database

| Rule                                                                                    | Mechanism                                        |
| --------------------------------------------------------------------------------------- | ------------------------------------------------ |
| Event status and `completed_at` / `cancelled_at` agree                                  | `CHECK`                                          |
| Listing price > 0; `0 ≤ quantity_available ≤ quantity_total`                            | `CHECK`                                          |
| Order `subtotal = unit_price × quantity`, `total = subtotal + buyer_fee`, fees in range | `CHECK`                                          |
| Payment and refund amounts > 0                                                          | `CHECK`                                          |
| Ledger lines are non-zero                                                               | `CHECK`                                          |
| Each ledger transaction has ≥ 2 lines and sums to 0                                     | deferred constraint trigger, checked at `COMMIT` |
| Ledger rows are never updated or deleted                                                | `BEFORE UPDATE OR DELETE` trigger                |
| A business event posts to the ledger at most once                                       | unique `idempotency_key`                         |
| One payment and one refund per order; unique gateway reference                          | unique indexes                                   |

`test/db/constraints.test.ts` proves each ledger rule and a sample of the checks against a real
database. Every case runs in a transaction that is rolled back, and uses
`SET CONSTRAINTS ALL IMMEDIATE` to make deferred triggers fire before the rollback.

## Indexes worth knowing

| Index                                             | Serves                                              |
| ------------------------------------------------- | --------------------------------------------------- |
| `orders (status, expires_at)`                     | expiry sweep: pending orders past their reservation |
| `orders (buyer_id, created_at DESC)`              | "my orders"                                         |
| `listings (event_id, status)`                     | event page                                          |
| `ledger_entries (account_id)`                     | balance of one account                              |
| `payment_notifications (payment_id, received_at)` | audit trail of one payment                          |

## Seed

`src/db/seed.ts` creates four users (two sellers, one buyer, one admin), three events (one
already under way, so it can be completed in a demo), seven listings and the three platform ledger accounts. It is idempotent (skips if users exist) and
runs in the one-off `migrate` container after `prisma migrate deploy`, before the api starts. It never creates orders or
ledger entries: those only come from real flows.

## Commands (from `apps/api`, or with `-w @tc/api` from the root)

```
npm run db:migrate    create/apply a migration in development
npm run db:deploy     apply pending migrations (Docker, CI)
npm run db:seed       seed demo data
npm run db:reset      drop and recreate the dev database
npm run db:studio     browse data in Prisma Studio
```
